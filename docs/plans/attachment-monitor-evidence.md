# 附件监视器误报：核验与修复方案

状态：方案已实施；核验记录保留如下。实施与验证结果见 `../attachment-and-cancellation-fix.md`。站点预设未调整。

## 1. 核验结论

提供的分析抓住了主要缺陷：正文污染了容器状态文本，随后弱文本匹配被附件存在这一事实升级成了阻断证据。但以下结论需要修正：

- `attachments` / `previews` 是 DOM 命中数，不是独立文件数，更不代表服务端上传、解析已完成。卡片与它内部的图片可能重复计数。
- 发送按钮可用、无进度节点、DOM 安静，并不能排除附件仍在读取或解析。
- 日志中的 `root_text` 已证明状态取样混入了请求正文；具体是否为 DeepSeek 镜像节点，需要实际 DOM 才能确定，不能仅凭日志断定。
- 不是只要开启工具调用或写了“读取”就一定触发。普通输入控件的正文会被排除，问题在于其他节点仍可能暴露正文、文件名等内容。
- 预设的 root/attachment/pending 选择器确实会影响检测范围，不能说与预设完全无关；根本修复应在通用监视器，而不是要求用户禁用 Tools、改写提示词或全局忽略 processing。
- 这是有超时上限的错误等待，不是已证实的线程死锁，也不能从日志推断固定存在一个 28 秒硬超时。

### 当前代码证据

`app/core/workflow/attachment_monitor.py`：

1. `defaultBusyWords` 包含裸词“读取”“分析”，英文使用子串匹配，`image_processing` 可命中 `processing`。
2. `getRootStatusText()` 克隆 root 并移除常见输入节点，但不可靠地排除镜像、隐藏元素和其他用户内容；克隆后的 `textContent` 仍会包含这些文字。回退路径也会重新读取原始 root。
3. `collectState()` 从整个 root 匹配忙碌词，不记录命中的文本来源。
4. `_is_ready_state()` 中 `pendingText && attachment_present` 即可阻断；存在附件不是上传繁忙的独立证据。
5. `derive_phase_flags()`、`explain_not_ready()`、等待循环各自重复判断 pending；仅修一个函数会产生相互矛盾的状态和日志。
6. `_has_meaningful_progress()` 把 root 文本变化与通用 mutation 计为进展；等待循环还会因持续 pending 刷新等待期限。
7. `summarize()` 可将正文片段写入 `root_text` 日志，存在不必要的信息泄露。

### 本地复现

使用实际 AttachmentMonitor JS 与 Python 就绪判定，在 Chromium 合成输入区测试。每项均有一个新插入的附件卡片；命中附件数和预览数均为 2，因为卡片与内层图片重复计数。所有场景 `pendingCount=0`，发送按钮可用。

| 场景 | pendingText | upload_ready |
|---|---:|---:|
| 普通正文 | false | true |
| textarea 正文含 processing / 读取，没有镜像 | false | true |
| 可见镜像复制相同正文 | true | false |
| 隐藏镜像复制相同正文 | true | false |
| 文件名为 image_processing_读取.txt | true | false |
| 附件状态节点真实显示“读取中” | true | false |

最后一行是必须保留的阻断：不能因为它没有进度条、按钮可用就当作完成。以上验证不等于真实 DeepSeek 上传或对用户 28 秒完整超时过程的端到端复现。

## 2. 修复原则

将“找到了词”改为“收集带来源的证据”，再由一处统一决策。

- 本次上传与旧附件分开。
- 正文、文件名、附件内容预览不是上传状态。
- 整个输入区的疑似词只作弱提示，不能单独阻断、确认开始、确认完成或续期。
- 真正的上传失败、进度指示、附件忙碌状态必须继续阻断。
- 状态不充分时不假定成功；保留超时和取消能力。
- 不自动重放文件粘贴、上传、点击或发送。

## 3. 检测与决策架构

### A. 明确当前批次和附件候选

保留 root 用来寻找相关 UI，但不再把 root 的全文视为状态文本。上传开始时记录基线与批次标识，建立当前新附件候选集合。

- 对同一卡片及其后代去重，避免一个文件计作多个附件。
- 结合本次上传的新增卡片、文件元数据和变化事件关联候选，不仅依靠文件名；同名文件不能合并。
- 旧附件、聊天历史、输入正文变化不作为本次上传的新鲜证据。
- 排除输入区及其子树、镜像、隐藏节点、提示词展示区。
- 检查自定义选择器是否命中了包含输入框的大容器。此类节点不可直接当作可信附件状态源，需要继续定位内部卡片，或发出范围过宽诊断。

不要求每个网站必须有相同 DOM；通过通用规则加可选的精确状态选择器实现适配。

### B. 为证据记录来源与可信度

建议内部结构：

```text
evidence:
  batch_id / attachment_id
  source: progress | attachment_status | send_state | root_text
  kind: busy | ready | rejected | unknown
  confidence: explicit | scoped | weak
  marker: 已识别的状态词或结构化属性
```

可信忙碌证据包括：与本批附件关联的进度节点、`aria-busy`、明确上传状态属性，或附件独立状态子节点的忙碌提示。

不能把整个卡片的 `textContent` 都当成状态：卡片内部同样可能含文件名和内容预览。应单独识别状态区域，并排除名称、正文、代码、OCR/文档内容预览；`role=status` 也需要检查是否关联当前附件，而不是无条件信任全页状态节点。

root 中的匹配只记录为弱提示。`pending_selectors` 的候选也必须做输入区域、可见性和当前批次过滤，避免只修文字而仍被编辑器内部的 loading 类名阻断。

### C. 收窄词匹配，但不依赖词表解决范围问题

- 默认中文状态词使用“读取中”“正在读取”“分析中”“正在分析”等，而非裸动词。
- 英文采用词边界或状态短语规则，避免 `image_processing`、文件名、代码标识符等子串误报。
- processing/loading 等合法状态词继续支持，但只有来源可信时才构成强证据。
- 保留现有自定义词表；不静默删除站点配置中的自定义项，也不允许扩大词表把 root 弱证据直接升级为强证据。
- 可增加可选 `status_selectors`、`content_exclusion_selectors`，不要求普通用户手工配置。

### D. 统一状态机和发送门禁

由一个 `evaluate_attachment_state()` 统一生成状态、阻断原因、进展标记和诊断；上传后等待与发送前 gate 共用它。

| 条件 | 决策 |
|---|---|
| 本批附件出现明确失败 | REJECTED，返回附件错误 |
| 本批附件有可信上传/读取/解析证据 | BUSY，继续等待，即使按钮可用 |
| 没有观察到本批附件，或监视器不可用 | UNKNOWN，不发送 |
| 只有 root/正文/文件名的词匹配 | 不能单独决定忙碌或就绪 |
| 本批附件证据完整，无真实忙碌/失败，满足稳定窗口及站点发送条件 | READY |

无显式完成标识的网站可使用明确标注的“UI 稳定推断”：新鲜附件证据、无可信繁忙/失败、发送状态和稳定窗口共同成立。这不是服务端完成证明。如果连可靠的附件范围或状态来源都无法建立，仍应 UNKNOWN 并要求进一步适配。

多个附件必须按本批候选综合判断；一项仍 BUSY/REJECTED，不能因为另一个附件已有预览就发送。文件输入框清空并不代表附件消失或失败。

### E. 只有真实进展才更新计时

- 真实进展：本批附件新增、上传阶段变化、进度数值变化、实际状态变化。
- 不算进展：持续命中同一个词、用户输入、光标闪烁、镜像更新、无关样式动画。
- 区分“最近一次实际进展”和“最近一次 DOM mutation”。
- 一直 BUSY 不得无限延长总截止时间；无进展超时和绝对超时保留，分别报告原因。
- 刷新观测不会重复触发上传，超时也不能自动重放。

## 4. 一并修复错误传播

日志还有一个次生问题：`attachment_upload_unconfirmed` 后，同一 request/task 因 session.status=error 又被归类为 ownership_lost，随后工具解析收到空文本。

当前所有权检查确实把 error 状态归入所有权丢失；旧线性工作流的 WorkflowError 分支也只对部分错误返回明确错误事件。不能只改附件检测而保留这一信息丢失链路。

方案：

1. 不可恢复的附件失败先在请求层原子登记原始错误，再将标签页标为不可复用。
2. 同一任务自己导致 session 进入 ERROR，仍要停止操作，但不把已登记的失败覆盖成“被其他任务抢占”。真正的所有权变化保护继续生效。
3. 区分请求执行结果与停止原因：例如请求 `failed / attachment_upload_unconfirmed`，清理原因 `session_unavailable`。并发取消与失败遵守已确定的终态，不事后强行改写。
4. 线性与结构化工作流都完整返回附件错误；保留原 TRY 的合法恢复边界，不能在重试发送时重放副作用。
5. Tools 层收到失败/取消时直接传递结果，不再把错误落成空字符串送入普通文本回退。正常非工具文本回答，以及合法工具/媒体输出不受影响。

## 5. 日志与兼容

默认日志只记录状态、来源、阻断代码、附件候选数量、进展时间及有限的已识别状态标记。

不输出 root 全文、Prompt、工具定义或文档内容预览；节点描述也要避免通过 title/aria-label 泄露正文。必要的诊断使用长度、哈希或明确脱敏的信息。

建议输出示意：

```text
state=READY source=ui_stable weak_text_ignored=2 current_items=1
state=BUSY source=attachment_status marker=读取中
state=UNKNOWN reason=attachment_scope_ambiguous
```

保留现有监视器公开字段，新增证据版本和来源字段；内部决策不再依靠旧 pendingText 布尔值猜测。注入监视器与 Python 端一并更新并重建当前观察器。老快照缺少来源时不得伪装成新规则已验证状态。

站点原有附件限制、传输方式、Tools 支持、发送确认、默认预设都保留，不为修复误报全局关闭检测。

## 6. 实施顺序与验收

1. 固化当前复现及危险反例测试。
2. 完成来源隔离、统一状态决策及有效进展计时，贯通上传等待和发送前 gate。
3. 修正原始错误传播、日志脱敏与兼容策略。
4. 最后评估 DeepSeek 等站点的精确选择器；不以站点专用关键词黑名单代替通用修复。

必须覆盖：

- 普通 Prompt、Tools 描述、隐藏/可见镜像、contenteditable、文件名及文件预览含 busy 词，不误阻断。
- 只有文本“读取中”、按钮可用且没有 progress 节点，仍阻断真实 BUSY。
- 多文件其中一项繁忙或失败，不提前发送；旧预览不冒充新上传。
- 输入框/镜像中的 pending 类名、无关动画不延长附件等待。
- 观察器丢失、重新挂载、状态来源不明、不匹配的上传证据，不产生假成功。
- 真实上传状态停止变化会按期限失败，错误码不被 ownership_lost 或空工具输出覆盖。
- 取消生效，未确认的上传不重放，发送最多按原安全策略执行。
- 断言日志不包含请求正文和工具描述。

完成本地回归后，再对实际 DeepSeek、Gemini 页面及用户 Tools 请求进行验证。关闭工具调用或要求避开“读取”等词，不作为正式解决方案。
